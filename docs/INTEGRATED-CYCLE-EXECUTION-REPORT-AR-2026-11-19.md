### اختبار عزل RLS داخل معاملات مؤقتة
أجريت اختبارين على قاعدة TEST، وأُغلقت كل معاملة بـ`ROLLBACK`:
1. أنشأت Tenant/فرعًا/مريضًا اصطناعيًا داخل معاملة مؤقتة، ثم حاكيت جلسة مالك المعمل الحالي. النتيجة: لا يرى أي صف من Tenant الاصطناعي (0)، ويرى Tenant طيبة الخاص به (1). شمل الاختبار الجداول: tenants, branches, patients, site_settings, tenant_usage, backup_runs.
2. أنشأت مريضًا اصطناعيًا في فرع آخر داخل معاملة مؤقتة، ثم حاكيت جلسة موظف الجعافرة. النتيجة: يرى فرعه المعيّن (1)، ولا يرى فرع بهتيم (0)، ولا يرى مرضى الفرع الآخر (0).

هذه اختبارات RLS مباشرة بمحاكاة claims داخل PostgreSQL، وليست اختبار مستخدم حقيقي عبر المتصفح، ولا تثبت عزل عميلين دائمين مع حسابي Auth منفصلين.

## 5. سلسلة Supabase Migrations — الحالة والمانع
- Supabase يعرض المigrations المطبقة 012–022 بإصدارات timestamp.
- الجدول التطبيقي `public.schema_migrations` ما زال يحمل baseline `1.0.0` فقط.
- تمت مطابقة baseline 001 على مستوى الجداول والأعمدة، كما هو موثق في `docs/BASELINE-RECONCILIATION-AR-2026-11-19.md`.
- لا يوجد مجلد `supabase/migrations/` في المستودع.
- بيئة التنفيذ الحالية لا تحتوي Supabase CLI (`supabase` command غير موجود)، ولا يوجد checkout محلي للمستودع يمكن تشغيل `supabase migration new` داخله.
- وفق تعليمات Supabase CLI v3، ملفات migrations القياسية تُنشأ عبر `supabase migration new` في `supabase/migrations/` بنمط timestamp، وأوامر قاعدة البيانات تستهدف المحلي افتراضيًا ما لم يُحدد `--remote=<project-ref>` صراحة.

**القرار الآمن:** لم أختلق timestamps، ولم أضع ملفات migrations يدوية مدعية أنها CLI-generated، ولم أستخدم `migration repair` أو `db push` أو أشغّل 001–011. لم يتغير أي سجل migration في TEST.  
الخطوة التقنية المطلوبة: توفير بيئة repo checkout مع Supabase CLI v3، ثم إنشاء/تطبيع السلسلة القياسية ومراجعتها محليًا، ومطابقة كل version مع TEST قبل أي repair أو تطبيق. لا يكفي تطابق أسماء الجداول لإثبات سلامة ترتيب الترحيلات.

## 6. سجل الوظائف المتبقية واعتمادياتها
| المجال | الحالة الحالية | الاعتماد الضروري قبل التنفيذ الآمن |
|---|---|---|
| ضوابط الخصم | غير مكتملة؛ الواجهة والخادم يقبلان خصمًا حتى إجمالي الفاتورة فقط | إعداد سياسة لكل Tenant، حد يحدده المالك، سبب إلزامي، آلية اعتماد تجاوز، وتعديل ذري لـRPC الاستقبال ومسار Offline مع حفظ السبب والموافق |
| إلغاء تحليل/زيارة | غير مكتمل | سياسة إلغاء قبل/بعد النشر، صلاحية الموظف/المالك، منع حذف السجلات، تحديث الفاتورة والرصيد، سجل تدقيق |
| الاسترداد المالي | غير مكتمل | جدول/مسار refund مستقل أو حركة مالية عكسية مضبوطة، ربط بالدفعة الأصلية، منع تجاوز المبلغ المسترد، idempotency، قيد يوم العمل، وتحديث المديونية |
| إغلاق اليوم والأجهزة | الإغلاق الذري موجود، وفحص Outbox المحلي موجود في الواجهة؛ لا يرى الخادم أجهزة Offline الأخرى | تسجيل الأجهزة ونقاط المزامنة/leases، سياسة انتهاء/إقرار لكل جهاز، قفل خادمي ذري مع منع التحصيل المتزامن، ومسار استثناء موثق لا يتجاوز عمليات معلقة |
| أعلام H/L | حقل flag موجود في النتائج؛ الحساب الآلي غير مكتمل | مخطط مرجعي معتمد (وحدة، جنس، عمر، حدود شاملة/غير شاملة، شروط)، بيانات سريرية معتمدة، لقطة المريض والمرجع في الزيارة، helper موحد واختبارات حدود |
| النسخ السحابي | النسخة الحالية محلية فقط (Cache + Outbox + Conflicts) | تصدير كامل tenant/branch من الخادم، manifest/checksum، تشفير ومفتاح استعادة، Storage private، سجل backup_runs، استعادة خادمية idempotent وتجربة استعادة كاملة |
| CMS | محرر المحتوى موجود؛ أضيف رفع صور مصدرًا فقط | تجربة رفع حقيقية بحساب مالك، مراجعة Renderer العام، preview على الموقع المنشور، سياسة تنظيف ملفات يتيمة/قديمة |
| الاشتراكات | الجداول وإدارة حالة الاشتراك موجودة | تعريف حدود الباقات، triggers/RPC لعدادات الاستخدام، احتساب storage، تنبيهات 80/100%، سياسة تعليق/انتهاء، دون تعطيل Offline محليًا |
| عزل العملاء | تم اختبار RLS مؤقتًا لمالك وموظف ضمن بيانات طيبة | إنشاء Tenant ثانٍ وحساب Auth مستقلين، ثم اختبارات API/Storage/RPC/بوابة المريض بين العميلين |
| Migration history | غير موحد قياسيًا | Supabase CLI v3 وcheckout محلي، baseline strategy ومراجعة drift، ثم repair/apply مخطط ومثبت |
| Secrets/Auth | لم تتغير | ضبط Origins والأسرار من Dashboard، وتفعيل leaked password protection بعد مراجعة الإعدادات |

## 7. نتيجة Advisors الحالية
- Security: ثلاث جداول RLS بلا سياسات مباشرة (مسارات خادمية مقصودة): `private.offline_visit_intake_receipts`، `public.portal_access_attempts`، `public.schema_migrations`. توجد دالة عامة واحدة `get_public_tenant_by_slug` و19 دالة SECURITY DEFINER متاحة للمستخدمين المسجلين؛ لم تُسحب صلاحياتها عشوائيًا لأن بعضها مسارات تشغيل/إدارة تتطلب تحققًا داخليًا. يلزم مراجعة كل grant مقابل فحص `auth.uid()`/العضوية/صلاحية المنصة. حماية كلمات المرور المسرّبة غير مفعلة.
- Performance: 77 FK بلا فهرس تغطية، 21 مجموعة سياسات permissive متداخلة، 3 سياسات auth initplan، و7 فهارس لم تستخدمها الإحصاءات. لا أحذف الفهارس غير المستخدمة في TEST الفارغة، ولا أدمج السياسات دون اختبار دلالتها.
- Health: لا توجد تنبيهات.
- لا تغييرات Advisor تم تطبيقها.

## 9. تدخلات مطلوبة لإزالة العوائق
1. توفير بيئة تنفيذ بها نسخة repo checkout وSupabase CLI v3، أو تشغيل نفس الأوامر من جهاز/بيئة موثوقة مرتبطة بالمستودع. لا ترسل كلمات مرور أو service-role keys في المحادثة.
2. من Supabase Dashboard: تفعيل Leaked Password Protection، ومراجعة Origins/Secrets للدوال الأربع وفق نطاقات النشر الفعلية.
3. تحديد السياسة التشغيلية للخصم: مالك المعمل يحدد الحد الأعلى؛ الافتراضي المقترح عند عدم الإعداد هو منع الخصم غير الصفري حتى ضبط السياسة، مع سبب إلزامي واعتماد المالك لأي تجاوز. لا أفرض نسبة رقمية من عندي.
4. اعتماد سياسة الإلغاء والاسترداد: هل يُسمح بإلغاء تحليل بعد بدء تشغيله؟ وبعد نشر التقرير؟ وهل الاسترداد كامل أو جزئي وفق ما تم تنفيذه؟ يلزم قرار تشغيلي قبل إطلاق زر مالي.
5. توفير/اعتماد مرجع التحاليل الطبي لكل parameter (الوحدة، العمر، الجنس، حدود المجال)؛ لا يمكن اختراع قيم مرجعية.
6. إنشاء حساب/معمل تجريبي ثانٍ عبر Auth لإكمال اختبار العزل الكامل؛ الاختبار المؤقت الحالي يثبت جزء RLS فقط.
