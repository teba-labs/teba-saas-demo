# دفعة 34 — تجهيز أرشفة الفروع وحماية الوصول

**الفرع:** `integration/unified-test-2026-11-19`  
**نقطة البداية:** `62c2d128eec3fe92a75c940c84af5c753a9de39c`

## نطاق التغيير
- أضيفت migration 023 لتعديل `private.can_access_branch`: يظل مالك المعمل النشط قادرًا على الوصول إلى تاريخ الفرع المؤرشف، بينما يشترط وصول الموظف أن يكون الفرع نشطًا بالإضافة إلى نشاط عضويتي المعمل والفرع.
- أصبح سياق المالك يحتفظ بقائمتين: `branches` للفروع النشطة المستخدمة في التشغيل، و`allBranches` لإدارة المالك والتاريخ. يظل الموظف محصورًا في الفروع النشطة المسموح بها.
- أضيف عرض حالة الفرع المؤرشف في مركز الإعدادات، مع أزرار أرشفة/إعادة تفعيل معطلة عمدًا حتى اختبار migration على TEST.
- أضيف اختبار static لعقد عدم الحذف وحفظ صلاحية المالك وفصل الفروع النشطة عن قائمة التاريخ.

## ضمانات عدم فقد البيانات
- لا توجد أوامر حذف أو إعادة كتابة لسجلات الفروع أو العضويات أو المرضى أو الزيارات أو النتائج أو الحركات المالية.
- لا يتم تعديل عضويات الموظفين عند أرشفة الفرع؛ قرار المنع خادمي من خلال `private.can_access_branch`.
- لا يزال مالك المعمل النشط يتجاوز شرط نشاط الفرع حتى يستطيع مراجعة التاريخ.

## حدود هذه الدفعة
- لم تُطبق migration على Supabase؛ لا يوجد اتصال بقاعدة TEST في هذه الدفعة.
- لذلك بقيت أزرار الأرشفة وإعادة التفعيل معطلة عمدًا (`BRANCH_ARCHIVE_READY=false`).
- الاختبار المضاف static فقط؛ لا يثبت سلوك PostgreSQL/RLS الفعلي ولا يحل محل اختبار حساب مالك وموظف على TEST.
- لم تُجر تغييرات على Dashboard القديمة أو ملفات تحليلات Excel.

## الاختبار المطلوب قبل تفعيل الأزرار
1. تطبيق migration 023 على بيئة TEST فقط بعد التحقق من سلسلة migrations وحالة القاعدة.
2. اختبار موظف نشط على فرع نشط: الوصول مسموح.
3. أرشفة الفرع في TEST: وصول الموظف إلى بيانات الفرع مرفوض.
4. حساب مالك المعمل: يستطيع قراءة تاريخ الفرع المؤرشف.
5. إعادة التفعيل: يعود وصول الموظف وفق عضوياته القائمة دون إنشاء عضويات مكررة.
6. التأكد من بقاء عدد السجلات ومعرفات الفروع والزيارات والنتائج والمدفوعات دون تغيير.
