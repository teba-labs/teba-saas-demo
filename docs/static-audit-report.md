# Taiba Smart Lab — مراجعة النسخة الأصلية قبل تحويلها إلى قالب SaaS محايد

**المصدر:** `teba-lab-main.zip` (الأرشيف المرفوع، 34 عنصرًا، 1,370,289 بايت محتوى غير مضغوط تقريبًا).  
**تاريخ الأرشيف داخليًا:** 14 نوفمبر 2026.  
**نوع المراجعة:** فحص ساكن للملفات، المسارات، المراجع، إعدادات الاتصال، توافق الواجهة مع مخطط Supabase الجديد، وبعض مسارات الأمان والمزامنة. لم يتم تشغيل النظام في متصفح متصل بقاعدة البيانات الجديدة، ولم يتم إجراء اختبارات مستخدمين فعلية.

## الخلاصة التنفيذية

النسخة الأصلية تحتوي على وظائف كثيرة يمكن الحفاظ عليها والاستفادة منها، لكنها **ليست متوافقة حاليًا مع مخطط Supabase الجديد بمجرد تغيير رابط الاتصال**. يوجد اختلاف في نموذج الهوية والصلاحيات والجداول والأعمدة والدوال، إضافة إلى اعتماد كبير على بيانات واسم وهوية طيبة وفرعين ثابتين. لذلك المطلوب هو إعادة تنظيم وبناء طبقة ربط موحدة، وليس مجرد إعادة تسمية الملفات.

## 1) جرد الملفات ووظائفها الحالية

| الملف/المسار | الوظيفة الظاهرة | الإجراء المقترح |
|---|---|---|
| `index.html` | موقع المعمل العام، صفحات المحتوى والحجز | تحويله إلى قالب عام تقوده إعدادات CMS لكل مستأجر |
| `app.js` | تفاعلات الموقع العام والحجز والرسائل | الإبقاء على الوظائف بعد إزالة بيانات طيبة الثابتة وربط الإعدادات الديناميكية |
| `data.js` | كتالوج تحاليل وأسعار ثابت خاص بطيبة | إخراجه من بيانات المنتج؛ تحميل الكتالوج من بيانات كل معمل |
| `features.js` | وظائف ومحتوى إضافي للموقع | مراجعة كل وظيفة وربطها بإعدادات المستأجر |
| `site_dynamic.js` | تعبئة الهوية ومحتوى الموقع من الإعدادات | إعادة بنائه على CMS الجديد، وإزالة القيم الافتراضية الخاصة بطيبة |
| `patient_portal.js` | البحث عن زيارة وعرض/تصدير التقرير | إعادة ربطه بآلية البوابة الآمنة والتقارير المنشورة فقط |
| `settings.html` (الجذر) | إدارة محتوى الموقع CMS | ربطه بجداول `site_*` الجديدة، لا بجداول قديمة |
| `super-admin.html` | لوحة مالك المنصة | إعادة ربط المصادقة والتحقق ودورة إنشاء المستأجر بالدوال الجديدة |
| `dashboard/admin.html` + `admin.js` + CSS | الإدارة المالية والداشبورد والتحليلات | الحفاظ على الوظائف، مع تحويلها من الفروع الثابتة وحقول الجداول القديمة إلى النموذج الجديد |
| `system/home.html` | بوابة دخول النظام والتنقل | إعادة بناء التحقق من الهوية والعضوية والفرع من قاعدة البيانات |
| `system/reception.html` | الاستقبال والمرضى والزيارات والتحصيل | إعادة ربط دورة الزيارة والفوترة والمدفوعات والعمل اليومي |
| `system/lab.html` + `lab.js` + CSS | شاشة المعمل والنتائج والطباعة والنشر | إعادة ربط النتائج بالـ parameters والـ snapshots وإصدارات التقارير |
| `system/tests_manage.html` | إدارة كتالوج التحاليل | استخدام `tests_catalog`, `test_prices`, `test_parameters` بدل نموذج الكتالوج القديم |
| `system/settings.html` | إعدادات التشغيل والفروع والموظفين والطباعة | إعادة ربطه بـ `lab_settings`, `print_settings`, `branches`, `staff_directory`, memberships وغيرها |
| `dashboard/config.js`, `system/config.js`, `config.js` | نسخ متطابقة لإعدادات الاتصال والهوية | استبدالها بتهيئة واحدة محايدة، لا تحتوي tenant ثابتًا أو مشروع إنتاج قديم |
| `dashboard/styles.css`, `system/styles.css` | نسختان متطابقتان | دمج/مشاركة CSS بعد اختبار عدم كسر الواجهات |
| `header.png`, `system/header.png` و`logo.png`, `system/logo.png` | أصول مكررة | نقل الأصول العامة إلى مجلد assets، وعدم تضمين هوية طيبة كهوية افتراضية |
| `test.html` | صفحة تجارب/مساعد منفصلة عن تدفق النظام | فصلها عن إصدار الإنتاج ومراجعة مفتاح API المكشوف قبل أي استخدام |
| `manifest.json`, `service-worker.js` | PWA والتخزين المؤقت والعمل دون إنترنت | إعادة ضبط المسارات والكاش، خصوصًا منع تخزين بيانات API الطبية في كاش عام |

## 2) مشكلات مؤكدة من الفحص

### حرجة — اتصال الواجهة بمشروع مختلف

- ملفات `config.js` الثلاثة متطابقة وتشير إلى مشروع Supabase الإنتاجي القديم `khjzoleiuiipyodpkieg`، وليس مشروع الاختبار الجديد `hgqwpykeazuzceeiumjg`.
- تغيير الرابط وحده غير كافٍ؛ الواجهة تستعمل جداول وأعمدة ودوال قديمة لا يوفّرها المخطط الجديد.
- الإجراء: إزالة إعدادات الاتصال المكررة، واعتماد إعداد واحد حسب بيئة التشغيل، مع فصل الاختبار عن الإنتاج صراحةً ومنع fallback إلى tenant ثابت.

### حرجة — عدم توافق نموذج الحسابات والصلاحيات

- الواجهة تستعلم من جدول `users` في مواضع متعددة، بينما المخطط الجديد لا ينشئ جدول `public.users`؛ ويستخدم `tenant_memberships`, `branch_memberships`, `staff_directory`.
- الواجهة تعتمد أدوارًا مثل `admin`, `reception`, `lab`, `super_admin`، بينما النموذج الجديد يعتمد `account_type` (`owner`/`employee`) وعضوية الفرع، مع سجل أسماء العاملين.
- الواجهة تستدعي RPCs: `verify_branch_password`, `create_employee`, `create_new_tenant`، وهذه الأسماء غير موجودة في SQL الجديد. المقابل الموجود لإنشاء المستأجر هو `public.platform_create_tenant` بتوقيع مختلف.
- الإجراء: بناء Auth/Authorization service واحد، وعدم اعتبار localStorage أو اختيار الفرع أو الدور في المتصفح مصدر صلاحية.

### حرجة — عدم توافق الجداول والأعمدة

الجداول التي يستعملها الكود ولا توجد في المخطط الجديد:
- `users`
- `offers` (المخطط يستخدم `site_offers`)

حاوية التخزين التي يستعملها الكود `lab-assets` غير موجودة ضمن الحاويات الأربع الجديدة (`tenant-reports`, `tenant-attachments`, `tenant-site-assets`, `tenant-backups`).

أمثلة على اختلافات الأعمدة:
- الكود يتوقع في `patients`: `name`, `age`, `age_type`, `gender`, `doctor_name`؛ المخطط الجديد يستخدم `full_name`, `age_years`, `sex`، ويضيف ربط الفرع وحقول تدقيق.
- الكود يتوقع في `visits`: `visit_id`, `visit_date`, `total_amount`, `paid_amount`, `discount`, `client_uuid`؛ المخطط الجديد يستخدم `id`, `visit_number`, `visit_work_date`, `workday_id`، ويفصل الفوترة والمدفوعات في `visit_billing` و`payments`.
- الكود يتوقع في `visit_tests`: `test_code`, `price_at_time`, `is_cancelled`؛ المخطط الجديد يستخدم `test_id`, `test_code_snapshot`, `test_name_snapshot`, `price_snapshot`, `technical_snapshot`, `status`.
- الكود يتوقع في `test_results`: `results_data` JSON لكل التحليل؛ المخطط الجديد يسجل نتيجة كل parameter في صف مستقل مع snapshot للوحدة والرينج والقيمة.
- CMS القديم يتوقع حقولًا مفردة داخل `site_settings` مثل `lab_name`, `logo_url`, `primary_color`؛ المخطط الجديد يخزن `public_content` و`theme_json` مع فصل `lab_settings` عن إعدادات الموقع.

**النتيجة:** يجب كتابة طبقة data access جديدة وربط كل شاشة بالعقد الجديد، لا محاولة ترقيع أسماء الأعمدة في أماكن متفرقة.

### عالية — الاعتماد على بيانات طيبة داخل القالب

- الاسم والشعار واسم الطبيب والعنوان والفروع والرسائل والأسعار موجودة داخل HTML/JS/CSS وملف بيانات التحاليل.
- الداشبورد يحتوي على أسماء الجعافرة وبهتيم ثابتة في قوائم وتقارير ومعادلات كثيرة، ويفترض وجود فرعين فقط.
- بعض الصفحات تحتوي هوية مختلفة متبقية مثل عنوان `معمل الشفاء` في `system/settings.html`.
- الإجراء: نقل كل بيانات الهوية والفروع والكتالوج والأسعار إلى إعدادات/بيانات المستأجر، وجعل الشاشات ديناميكية لأي عدد فروع ضمن الحد المعتمد.

### عالية — احتمال فقد بيانات المزامنة

- محركات Outbox مكررة داخل `system/lab.js`, `system/reception.html`, `system/tests_manage.html` بدل محرك مركزي واحد.
- توجد عمليات Supabase لا تفحص `error`، ثم تحذف العملية من Outbox؛ مثال واضح في `system/reception.html` و`system/tests_manage.html`.
- بعض العمليات المالية تستخدم نمط «ابحث ثم أضف/حدّث» دون idempotency key موحد، وقد تتكرر أو تضيع عند انقطاع/إعادة المحاولة.
- الإجراء: محرك Outbox موحد مع operation UUID، ترتيب تبعيات، تأكيد نتيجة الخادم قبل حذف العملية، retry/backoff، وتسجيل تعارضات منفصلة. المعاملات المالية والنتائج الطبية لها قواعد خاصة، وليس last-write-wins.

### عالية — Service Worker يخزّن طلبات GET عامة

- `service-worker.js` يعترض كل طلبات GET ويضع أي استجابة HTTP 200 في `RUNTIME_CACHE`، دون استثناء Supabase REST أو البيانات الطبية الخاصة.
- الكاش لا يبدو مقسمًا حسب المستخدم/المعمل، ولا توجد آلية واضحة لمسح بيانات API الخاصة عند تسجيل الخروج أو تبديل الحساب.
- fallback الخاص بالتنقل يعيد Promise من `caches.match('./system/home.html')` قبل محاولة `index.html`، لذلك fallback الثاني لا يعمل كما يبدو مقصودًا.
- الإجراء: كاش للأصول الثابتة فقط، ومنع تخزين Auth/API/نتائج المرضى في Cache Storage. بيانات الأوفلاين تبقى في IndexedDB مع tenant/branch scope والتحقق من الجلسة.

### عالية — مفتاح API داخل صفحة تجارب

- `test.html` يحتوي على مفتاح API لخدمة ذكاء اصطناعي مكتوبًا مباشرة داخل JavaScript.
- لا يُعاد استخدامه في القالب، ويجب إلغاؤه/تدويره من مزود الخدمة قبل أي نشر إذا كان ما زال فعالًا. لا نضع مفاتيح خدمات الذكاء الاصطناعي السرية في المتصفح؛ تستخدم خدمة وسيطة آمنة.

### متوسطة — مسارات أصول مكسورة/غير موجودة

- `index.html` و`system/home.html` و`system/reception.html` تطلب `brand-logo.png`، لكنه غير موجود في الأرشيف.
- `manifest.json` يشير إلى `brand-logo.png` بأحجام 192 و512، لكنه غير موجود.
- `service-worker.js` يحاول precache هذا الملف غير الموجود.
- `test.html` ملف تجريبي لا يظهر كجزء من رحلة المستخدم الأساسية.

### متوسطة — التكرار والتنظيم

- `config.js` متكرر ثلاث مرات ومحتواه مطابق.
- `dashboard/styles.css` و`system/styles.css` متطابقان تمامًا.
- `logo.png` و`system/logo.png` متطابقان، وكذلك `header.png` و`system/header.png`.
- عدة صفحات تحتوي JavaScript وCSS داخليين كبيرين؛ هذا يجعل الاختبار والصيانة وإعادة استخدام الوظائف أصعب.

## 3) الفحوصات الساكنة التي نجحت

- جميع ملفات JavaScript الخارجية اجتازت `node --check` دون أخطاء صياغة.
- كل كتل JavaScript الداخلية المستخرجة من صفحات HTML اجتازت `node --check` دون أخطاء صياغة.
- لم تُكتشف معرفات HTML (`id`) مكررة داخل الصفحة الواحدة.
- لا توجد مراجع محلية مفقودة للـ `script` أو `link`؛ توجد مراجع صور مفقودة محددة أعلاه.

هذه النتائج لا تثبت سلامة منطق التشغيل أو توافق قاعدة البيانات أو أمان RLS.

## 5) ترتيب التنفيذ المقترح

1. تثبيت نسخة المصدر الأصلية كما هي، وحفظ بصمتها (hash) وعدم تعديلها.
2. إنشاء نسخة تطوير مستقلة باسم محايد، مع تقرير يربط كل ملف قديم بمكانه الجديد.
3. فصل صفحات الموقع العام، النظام الداخلي، الداشبورد، CMS، ومسؤول المنصة إلى وحدات واضحة.
4. توحيد Supabase client وAuth/tenant/branch context.
5. بناء data access layer مطابق للمخطط الجديد، مع mapping واضح للحقول القديمة إلى الجديدة.
6. نقل بيانات طيبة والفروع والأسعار والصور من القالب إلى بيانات المستأجر/الإعدادات؛ عدم تضمينها كقيم افتراضية.
7. إعادة بناء المزامنة والأوفلاين، ثم اختبار عدم التكرار وفقد البيانات والتعارضات.
8. إعادة بناء بوابة المريض والتقارير وStorage حسب الدوال والسياسات الجديدة.
9. اختبار كل صفحة ووظيفة على مشروع الاختبار بحسابات فعلية متعددة الأدوار والمعامل والفروع.
10. بعد اجتياز الاختبارات، إعداد ZIP محايد كامل للنشر.

## 6) أسئلة فقط عند وجود غموض وظيفي حقيقي

لن نعيد سؤال المستخدم عن القرارات التي سبق اعتمادها. سنطلب توضيحًا فقط إذا كشف الكود عن سلوك غير موثق يؤثر في قرار التنفيذ، مع ذكر اسم الملف والزر والسلوك المتعارض تحديدًا.
