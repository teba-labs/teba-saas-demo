# Taiba Smart Lab — المراجعة الوظيفية والتقنية المجمّعة

**تاريخ المراجعة:** 18 نوفمبر 2026  
**المستودع:** `teba-labs/teba-saas-demo` — `main`  
**قاعدة الاختبار:** `hgqwpykeazuzceeiumjg` — `teba-lis-demo`  
**الحالة:** اكتملت مراجعة المصدر والبنية الفعلية مبدئيًا. لم تُجرَ تعديلات تشغيلية أو SQL في هذه المراجعة.

> هذا التقرير هو مرجع نتائج التدقيق قبل بدء دفعات الإصلاح. لا يخلط بين وجود الوظيفة في المصدر وبين نجاح تشغيلها ميدانيًا.

## 1. منهج التحقق وحدود الأدلة

استُخدمت أربعة أنواع من الأدلة:
- **مصدر المستودع:** قراءة صفحات HTML وJavaScript والمستودعات وملفات SQL والمigrations والاختبارات والوثائق.
- **قاعدة TEST الفعلية:** قراءة بنية الجداول والسياسات والدوال والمحفزات والفهارس والبيانات التجميعية، مع اختبارات قراءة فقط.
- **النسخة المنشورة:** قراءة نسخ Edge Functions المنشورة ومقارنتها بمصدر GitHub.
- **المعاينة التي أبلغ بها المستخدم:** أفاد المستخدم بأنه دخل بصفته مالك المنصة وظهرت له تفاصيل اشتراك معمل طيبة. لم أشاهد شاشة المستخدم بنفسي.

**ما لم يُنفذ:** لا اختبار متصفح جديد، ولا اختبار تشغيل كامل لمريض/زيارة/نتيجة/تقرير، ولا اختبار عزل بين عميلين مختلفين، ولا استدعاء حيّ لـEdge Functions. أرقام الاختبارات الثابتة 104/104 المذكورة في سجل الدفعة السابقة تاريخية ولم أعد تشغيلها في هذه الجلسة.

## 2. الحالة الفعلية الحالية لطيبة في قاعدة TEST

تم التحقق من وجود:
- معمل طيبة بحالة `active`.
- فرعين مسجلين.
- 3 عضويات معمل نشطة: مالك وموظفان.
- عضويتين نشطتين على مستوى الفروع.
- اشتراك بحالة `active` وخطة «باقة الجامبو» بسعر شهري 350 جنيهًا. تاريخ الانتهاء ونهاية التجربة غير محددين.
- المستخدم أكد ظهور تفاصيل الاشتراك في لوحة مالك المنصة.

لكن **قاعدة الاختبار ليست جاهزة بعد لتشغيل رحلة معمل حقيقية**. أعداد السجلات التشغيلية الحالية للمعمل:

| العنصر | العدد الحالي |
|---|---:|
| أسماء موظفين في `staff_directory` | 0 |
| تحاليل نشطة | 0 |
| بارامترات فنية نشطة | 0 |
| أسعار حالية | 0 |
| أيام عمل مفتوحة | 0 |
| مرضى | 0 |
| زيارات | 0 |

لذلك لا يمكن حاليًا تنفيذ استقبال حقيقي أو فتح يوم عمل أو تشغيل النتائج، حتى لو كانت صفحاتها تفتح. يلزم أولًا استكمال إعداد المعمل والكتالوج والموظفين.

**اختبار صلاحيات محدود داخل TEST:** عند محاكاة حساب موظف موجود، ظهرت له بيانات فرع واحد فقط، ولم يُعامل كمالك. وعند محاكاة حساب المالك، ظهرت له الفروع الاثنان. هذا يدعم صحة نطاق الفروع داخل المعمل الواحد. لكنه لا يثبت العزل بين عميلين؛ لا يوجد حاليًا عميل ثانٍ للاختبار.

## 3. خريطة الوظائف حسب الدور

### 3.1 مالك المنصة

**الموجود:**
- دخول مستقل في `app/platform-admin.html`.
- قائمة المعامل عبر RPC محمي يتحقق من صفة مالك المنصة.
- إنشاء معمل لحساب Auth موجود مسبقًا.
- إدارة بيانات الباقات وحالتها.
- تعديل حالة المعمل والاشتراك والباقة.
- قائمة المنصة تعرض بيانات مجمعة، ولا تطلب أسماء المرضى أو نتائجهم أو ملفات تقاريرهم أو قيودهم المالية التفصيلية.

**النواقص/المخاطر:**
1. إنشاء المعمل لا ينشئ فرعًا افتراضيًا، ولا ينشئ موظفين أو صلاحيات فروع أو كتالوجًا؛ لذلك العميل الجديد لا يستطيع بدء التشغيل من واجهة المنصة وحدها.
2. لا توجد واجهة لدعوة مالك المعمل أو إنشاء حسابات Auth؛ يجب أن يكون حساب المالك مسجلًا مسبقًا خارج هذه الرحلة.
3. لا توجد واجهة مكتملة لإدارة انتهاء الاشتراك وتواريخه؛ الشاشة الحالية تعدّل الحالة والباقة أساسًا.
4. `limits_json` و`features_json` محفوظان في تعريف الباقة، لكن لم يظهر تطبيق فعلي يفرض حدود عدد المرضى/الفروع/التخزين أو يوقف الميزات حسب الباقة.
5. عدادات `tenant_usage` تُقرأ في لوحة المنصة، لكن لا توجد محفزات على الجدول ولا مسار تحديث تلقائي ظاهر في الدوال؛ العداد الحالي صفر. بالتالي لا ينبغي الاعتماد على أرقام الاستخدام الحالية للفوترة أو الإنذارات.
6. لا توجد واجهة طلب دعم وموافقة عميل كاملة. جداول `support_requests` و`support_grants` موجودة، لكن منح الدعم لا يدخل في دالة صلاحيات الفروع ولا يمنح وصولًا فعليًا محدودًا ومؤقتًا.
7. تعليق/إيقاف المعمل أو انتهاء الاشتراك لا يمنع حاليًا دخول التطبيق الداخلي؛ تفاصيل ذلك في قسم الأمان.

### 3.2 مالك المعمل

**الموجود:**
- لوحة مالية شهرية في `app/dashboard.html`.
- إعدادات هوية المعمل والتواصل والتذييل ورسالة واتساب.
- كتالوج التحاليل والأسعار.
- محرر محتوى الموقع.
- مركز المزامنة والنسخ المحلي.
- الاطلاع على الفروع المسجلة من مركز الإعدادات.

**النواقص:**
- لا توجد إدارة فروع فعلية (إضافة/تعديل/تعطيل) داخل الواجهة؛ الموجود عرض للفروع.
- لا توجد إدارة مستخدمين ودعوات Auth وعضويات الفروع من الواجهة.
- `staff_directory` يحتوي أسماء تشغيلية فقط، وليس حسابات دخول. وهو غير مربوط تلقائيًا بهوية Auth التي نفذت العملية.
- لا توجد إدارة لبنود المصروفات.
- لا توجد واجهة لحفظ إعدادات الطباعة؛ المستودع يحتوي قراءة `getPrintSettings` فقط.
- لا توجد واجهة لرفع شعار المعمل، رغم وجود `logo_path` في الإعدادات.
- لا توجد شاشة لعرض سجل التعديلات رغم وجود `audit_logs`.
- لا توجد إعدادات مستقلة لبوابة المريض.
- لا توجد نسخة احتياطية سحابية للمعمل أو استعادة كاملة من السحابة.

**مشكلة انتقال الفرع بين الشاشات:** اختيار الفرع في الصفحة الرئيسية لا يُمرر إلى صفحات الاستقبال والنتائج ويوم العمل والمزامنة؛ هذه الصفحات تبدأ غالبًا بأول فرع في القائمة. لذلك قد يختار المستخدم فرعًا في المدخل ثم يفتح شاشة تعمل على فرع آخر دون أن ينتبه. يجب توحيد سياق الفرع المختار بين الشاشات.

### 3.3 الموظف

**الموجود:**
- دخول عبر Auth وعضوية معمل/فرع.
- الاستقبال والزيارات.
- إدارة البيانات الفنية للكتالوج والبارامترات.
- يوم العمل والمصروفات.
- إدخال النتائج وإنهاء التحاليل واعتماد الزيارة ونشر التقرير.
- مركز المزامنة.

**نقطة صلاحيات مهمة:**
النظام الحالي يميز في الأساس بين `owner` و`employee`. لا توجد أدوار منفصلة للاستقبال والفني والمراجع. لذلك الموظف المصرح له بالفرع يستطيع تنفيذ أغلب وظائف الفرع، بما فيها اعتماد النتائج ونشر التقرير، وليس فقط وظيفة الاستقبال أو الفني.

كذلك واجهة لوحة المالك مخفية عن الموظف، لكن سياسات RLS تسمح لعضو الفرع بقراءة `financial_ledger` و`payments` و`expenses` وبيانات الفواتير ضمن فرعه. أي أن إخفاء لوحة المالك في الواجهة لا يساوي منع قراءة بياناتها من API. يلزم حسم سياسة مالية واضحة: هل يرى الموظف حركة الشفت فقط، أم كل الحركات التاريخية والتفصيلية؟ التوصية هي توفير ملخص محدود للشفت عبر RPC بدل كشف الجداول المالية كاملة.

### 3.4 المريض

**الموجود:**
- صفحة مستقلة `portal/index.html`.
- البحث برابط المعمل + الاسم المطابق + رقم الزيارة.
- إرجاع أحدث تقرير منشور فقط عبر رابط موقّع قصير الصلاحية.
- رسائل فشل عامة لا تكشف هل المريض أو الزيارة موجودان.

**النواقص:**
- لا توجد واجهة إعدادات مستقلة للبوابة أو إدارة نطاقاتها من داخل المعمل.
- لم يتم اختبار الاستعلام الحي أو صلاحية الرابط أو انتهاء صلاحيته في المتصفح.
- مصدر GitHub للوظيفة المنشورة قديم مقارنة بالنسخة الفعلية المنشورة؛ التفاصيل في قسم النشر.

## 4. تتبع دورة التشغيل الأساسية

### 4.1 إنشاء المعمل وتجهيزه

المسار الحالي ينشئ Tenant وعضوية المالك وإعدادات المعمل والموقع وسجل الاستخدام والاشتراك التجريبي. لكنه لا ينشئ فرعًا أو موظفين أو كتالوجًا أو أسعارًا. كما لا توجد شاشة مالك المعمل لإكمال هذه العناصر.

**الحكم:** إنشاء سجل العميل موجود؛ تهيئة عميل جاهز للتشغيل غير مكتملة.

### 4.2 يوم العمل

**الموجود:**
- فتح اليوم وإغلاقه عبر RPC.
- قيد واحد مفتوح لكل فرع enforced بفهرس فريد جزئي.
- تسجيل المصروف عبر RPC مع مفتاح منع التكرار.
- دفتر الحركة يُنشأ من حركات الدفع والمصروفات، وليس من إدخال يدوي مباشر.
- الإغلاق يحفظ لقطة تشمل التحصيل والمصروفات والصافي وعدد الحالات والتحاليل والمديونيات.

**النواقص:**
- لا يوجد إدخال للمبلغ النقدي الفعلي الذي عُدّ عند الإغلاق؛ الإغلاق الحالي لقطة حسابية من النظام وليس مطابقة نقدية فعلية.
- لا توجد إدارة لبنود المصروفات.
- لا توجد شاشة تاريخ إغلاقات متكاملة؛ يظهر آخر إغلاق فقط.
- لا يوجد تحقق يمنع إغلاق اليوم بينما توجد عمليات Offline معلقة لم تُزامن بعد. قد تصل عملية مصروف/زيارة بعد الإغلاق فترفضها قواعد يوم العمل وتتحول إلى تعارض.
- فتح/إغلاق اليوم Online-only.

### 4.3 الاستقبال والفاتورة والتحصيل

**الموجود:**
- بحث المريض داخل الفرع وتسجيل مريض جديد.
- اختيار التحاليل من الكتالوج.
- إنشاء الزيارة ولقطات الأسعار والبارامترات والفاتورة والدفعة الأولى في RPC واحد ذري.
- يتحقق الخادم من السعر الحالي؛ وإذا تغير السعر منذ حفظ العملية Offline لا يعيد تسعيرها بصمت، بل يرفضها كتعارض.
- إنشاء المريض منفصل عن إنشاء الزيارة، مع اعتماديات Outbox تمنع إرسال الزيارة قبل تأكيد إنشاء المريض.

**النواقص/المخاطر:**
1. طريقة الدفع في واجهة الاستقبال ثابتة على `cash`؛ لا يوجد اختيار بطاقة أو محفظة أو تحويل، رغم أن قاعدة البيانات تدعم هذه الأنواع.
2. الخصم متاح للموظف حتى قيمة إجمالي الفاتورة؛ لا يوجد حد نسبة أو سبب أو موافقة مدير.
3. قاعدة البيانات تدعم سعرًا عامًا وسعرًا خاصًا بفرع، لكن واجهة الاستقبال تجلب الأسعار دون تمرير الفرع، وتحوّل النتائج إلى خريطة حسب التحليل فقط. إذا وُضع سعر خاص لفرع، قد تعرض الواجهة سعرًا غير مطابق للسعر الذي سيعتمده الخادم، فتُرفض الزيارة كتعارض سعر.
4. يوجد RPC في قاعدة TEST للسعر الخاص بالفرع لكنه غير موجود في ملفات migrations/عقد الكود الحالي.
5. توجد دالة `recordPayment` في مستودع الاستقبال، لكن لا توجد شاشة تستخدمها لتسجيل تحصيل لاحق للمديونية؛ واجهة الاستقبال تسجل الدفعة الأولى فقط.
6. لا توجد في الواجهة الحالية دورة واضحة لتعديل بيانات المريض أو إلغاء الزيارة/رد المبلغ أو طباعة إيصال مستقل.

### 4.4 النتائج واعتماد الزيارة

**الموجود:**
- شاشة عمل للتحاليل.
- إدخال رقمي أو نصي أو نعم/لا أو اختيار من قائمة.
- حفظ مجموعة نتائج التحليل في RPC ذري واحد.
- لقطة التحليل تحفظ الاسم والوحدة والمدى والاختيارات حتى لا يغيّر تعديل الكتالوج نتائج الزيارات القديمة.
- قاعدة البيانات تتحقق من نوع القيمة والبارامتر ضمن اللقطة.
- تصحيح النتيجة المنشورة يحتاج سببًا موثقًا.

**نقطة مهمة تم التحقق منها وتصحيح فهم أولي سابق:**
- زر إنهاء التحليل وزر اعتماد الزيارة ينفذان تحديثات مباشرة من الواجهة، وفحوص اكتمال النتائج/حالة التحاليل موجودة في JavaScript وليست انتقالًا ذريًا مستقلًا في RPC.
- لكن **بوابة نشر التقرير في قاعدة البيانات أقوى من ذلك**: محفز `validate_report_version_publication` يتحقق عند إنشاء النسخة المنشورة من أن هناك تحاليل مطلوبة، وأن كل تحليل غير ملغى حالته `completed`، وأن كل بارامتر إلزامي له نتيجة. لذلك لا يكفي تغيير حالة الزيارة يدويًا لنشر تقرير ناقص.
- النقص المتبقي هو أن حالات `completed` و`approved` نفسها يمكن أن تصبح مضللة قبل النشر؛ يجب نقل الانتقالات إلى عمليات قاعدة بيانات محمية وذرية، مع تسجيل الموظف المنفذ والتحقق من الصلاحية داخل الخادم.

**نواقص أخرى:**
- لا يوجد تمييز بين فني ومدقق/مراجع؛ أي موظف فرع يستطيع إدخال النتائج واعتماد الزيارة.
- لا يوجد حساب تلقائي لعلامة مرتفع/منخفض؛ الواجهة ترسل `flag = null` وتعرض المدى النصي فقط.
- قائمة العمل تجلب كل التحاليل غير الملغاة دون حد زمني أو ترقيم صفحات، وترتب من الأقدم. بعد نمو البيانات قد لا تظهر أحدث التحاليل بسبب حد الصفوف في API.
- تحميل النتائج يتم بطلب منفصل لكل تحليل وبشكل متتابع (N+1)، ما يزيد زمن الشاشة مع كثرة التحاليل.
- بعد تصحيح نتيجة منشورة، يتم حفظ التصحيح أولًا ثم رفع PDF جديد في عملية منفصلة. إذا فشل رفع النسخة الجديدة، تظل قاعدة النتائج مصححة بينما أحدث PDF متاح للمريض هو النسخة القديمة. الواجهة تحذر من ضرورة إعادة الرفع، لكن المسار ليس عملية واحدة محكمة.

### 4.5 نشر التقرير وبوابة المريض

**الموجود والمتحقق من المصدر المنشور:**
- Edge Function `publish-report` نشطة، وتطلب JWT، وتتحقق من المستخدم، وتقبل PDF حتى 10 ميجابايت، وترفعه إلى Bucket خاص، ثم تستدعي RPC النشر.
- مصدر GitHub لوظيفة `publish-report` مطابق تمامًا للمصدر المنشور وقت الفحص.
- نسخ التقارير غير قابلة للتعديل/الحذف من المسار العادي، وكل نشر ينشئ إصدارًا جديدًا.
- Bucket التقارير خاص، وسياسات التخزين تربط الوصول بالمعمل والفرع والزيارة.

**ملاحظة مهمة عن بوابة المريض:**
- Edge Function `patient-portal-lookup` نشطة في Supabase، ونسختها المنشورة تستخدم RPC ذريًا اسمه `consume_patient_portal_attempt` لحساب المحاولات، وتخزن بصمات HMAC بدل الاسم وعنوان IP الخام، وتعيد رابطًا موقّعًا لمدة 120 ثانية.
- **ملف GitHub الحالي مختلف وأقدم**: ما زال يستخدم عدًّا ثم إدخالًا منفصلين للمحاولات، وهو معرض لسباق الطلبات المتزامنة. كما أن README الخاص به يقول إنه لم يُنشر، رغم أن النسخة المنشورة نشطة.
- RPC `consume_patient_portal_attempt` موجود في قاعدة TEST لكنه غير موجود في أي migration بالمستودع. نشر نسخة GitHub الحالية فوق النسخة المنشورة سيعيد limiter أضعف؛ لا تفعل ذلك قبل توحيد المصدر.

**ما لم يُختبر:** استدعاء Edge Functions فعليًا، إعداد الأسرار وقائمة Origins، رفع PDF حقيقي، ورابط المريض من متصفح خارجي.

### 4.6 لوحة المالك والتحليل المالي

**الموجود:**
- تقرير شهري للفواتير والخصومات وصافي الفواتير والتحصيل الفعلي والمصروفات والمديونيات.
- مقارنة الفروع والحركة اليومية وأكثر التحاليل طلبًا.
- يوضح النظام أن صافي النقدية ليس صافي الربح، ولا يخترع هامش ربح دون تكلفة تحليل موثوقة.

**النواقص:**
- الاستعلامات لا تستخدم pagination؛ قد تصبح المجاميع غير مكتملة عند تجاوز حد الصفوف الافتراضي في API.
- الزيارات والتحاليل الملغاة لا تُستبعد من بعض العدادات وتجميع أكثر التحاليل حركة.
- قيمة التحليل في قائمة الأكثر حركة هي مجموع سعر اللقطة قبل توزيع خصم الفاتورة، وليست صافي إيراد التحليل بعد الخصم.
- لا توجد بعد تقارير سنوية/BCG/ربحية تحليل/خطة شهر/توقعات/استيراد Excel. هذه مرحلة تحليلية لاحقة وليست سببًا لتأخير سلامة دورة التشغيل الأساسية.

### 4.7 الموقع العام CMS

**الموجود:**
- محرر ثماني مجموعات: الأقسام، التحاليل المعروضة، الباقات، المقالات، الأسئلة، التقييمات، العروض، وفروع الموقع.
- فصل أسعار الموقع المعروضة عن أسعار التشغيل والفواتير.
- RLS يسمح للمالك بالإدارة، ويقصر القراءة العامة على المحتوى المنشور وفق حالة كل مجموعة.
- يوجد Loader في `website/public-site.js` لجلب المحتوى المنشور.

**النواقص:**
- لا توجد صفحة HTML/واجهة عامة كاملة للموقع داخل هذا المستودع؛ الموجود محرر وطبقة تحميل بيانات فقط. يمكن أن يستهلكها موقع خارجي، لكن ذلك غير مثبت هنا.
- لا يوجد رفع صور/شعار من المحرر؛ الحقول تحفظ مسارات نصية.
- لا توجد معاينة عامة قبل النشر أو ربط نطاق العميل من داخل النظام.

### 4.8 الإعدادات والملفات والسجل

- إعدادات المعمل الحالية تحفظ الهوية والتواصل والتذييل ورسالة واتساب.
- عرض الفروع فقط، دون إدارتها.
- إعدادات الطباعة قراءة فقط ولا يوجد مسار حفظ ظاهر.
- لا يوجد رفع شعار.
- توجد محفزات Audit على جداول تشغيلية مهمة مثل المرضى والزيارات والنتائج والمدفوعات والمصروفات والأسعار والتقارير والفروع والإعدادات.
- لا توجد شاشة لقراءة Audit Logs.
- لا تظهر محفزات Audit على جداول المعامل والاشتراكات والباقات وعضويات المستخدمين وطلبات/منح الدعم؛ لذلك تغييرات المنصة والصلاحيات لا تملك سجلًا مكافئًا حاليًا.

## 5. Offline والمزامنة والنسخ

**ما هو موجود:**
- Service Worker يخزن ملفات التطبيق الثابتة وملفات ESM، ولا يخزن ردود Supabase أو بيانات المرضى من API.
- Dexie يخزن بيانات محلية محددة حسب المعمل والفرع.
- Outbox يدعم معرفات عمليات ثابتة، واعتماديات، وحجز العمليات، وإقرار الخادم قبل حذف العملية.
- العمليات المدعومة حاليًا في المزامنة: إنشاء المريض، تسجيل الزيارة، التحصيل، والمصروف.
- مزامنة أفضلية أثناء بقاء صفحة تشغيل مفتوحة: عند عودة الإنترنت، وتغير حالة ظهور الصفحة، وكل 30 ثانية.

**الحدود والمشكلات:**
1. هذا ليس Background Sync حقيقيًا يعمل بعد إغلاق المتصفح؛ هو مزامنة دورية ما دامت صفحة من صفحات التشغيل مفتوحة.
2. إدخال النتائج واعتمادها ونشر التقرير وتعديل الكتالوج وفتح/إغلاق يوم العمل وCMS ولوحة المالك ما زالت Online-only.
3. مركز المزامنة يعرض التعارضات لكنه لا يوفر حلًا لها أو تعديل العملية وإعادة إرسالها؛ زر إعادة المحاولة يعيد العمليات الفاشلة فقط، لا المتعارضة.
4. قد يتعارض إرسال زيارة/مصروف محفوظ Offline إذا أُغلق يوم العمل قبل وصوله للخادم.
5. النسخة الاحتياطية JSON محلية وغير مشفرة. SHA-256 يتحقق من التطابق/التلف العرضي، لكنه ليس تشفيرًا ولا إثبات أصالة ضد من يستطيع تعديل الملف.
6. الاستعادة تدمج السجلات المحلية ولا تمثل استعادة كاملة مطابقة لحالة سابقة، ولا ترفع البيانات للسحابة.
7. يوجد Bucket خاص للنسخ وجدول `backup_runs`، لكن لا توجد آلية رفع/جدولة/استعادة سحابية مستخدمة في الكود.
8. بيانات المرضى والكاش المحلي لا تُمسح عند تسجيل الخروج، ولا يظهر حد احتفاظ أو تشفير للتخزين المحلي. هذا يحتاج سياسة للأجهزة المشتركة.
9. إذا كان المتصفح يقول إنه Online لكن طلب تحميل سياق المعمل يفشل بسبب شبكة متقطعة، لا يحاول `loadMyTenantContext` الرجوع للكاش؛ الرجوع يحدث فقط عندما `navigator.onLine === false`.

## 6. الأمان والعزل الفعلي

### نقاط جيدة تم التحقق منها
- جميع جداول `public` البالغ عددها 46 عليها RLS وFORCE RLS.
- صلاحيات anon المباشرة لقراءة المرضى والزيارات والنتائج والتقارير الخاصة غير ممنوحة.
- لا يستطيع authenticated الكتابة مباشرة إلى دفتر الأستاذ أو المدفوعات أو المصروفات أو أيام العمل؛ العمليات المالية الأساسية تمر عبر RPCs.
- Buckets التقارير والمرفقات والنسخ الخاصة غير عامة، وسياسات التخزين تربط المسارات بالمعمل/الفرع.
- دوال المنصة تتحقق من `is_platform_admin()`; ودوال التشغيل تتحقق من هوية المستخدم وصلاحية الفرع والموظف النشط. تحذير Security Advisor عن SECURITY DEFINER لا يعني وحده وجود ثغرة؛ يجب تقييم كل دالة مع حارسها.
- ثلاثة جداول بلا سياسات RLS هي سجلات داخلية/خاصة مقصودة: `private.offline_visit_intake_receipts` و`public.portal_access_attempts` و`public.schema_migrations`، ولا توجد صلاحيات قراءة للـanon/authenticated على سجلات المحاولات.

### فجوات أمن/تحكم عالية الأولوية
1. `private.is_tenant_member` و`private.is_tenant_owner` و`private.can_access_branch` لا تتحقق من حالة Tenant أو الاشتراك، كما أن `can_access_branch` لا تتحقق من `branches.is_active`. إيقاف الاشتراك أو تعليق المعمل أو تعطيل الفرع يخفيه من بعض الواجهات/الموقع العام، لكنه لا يوقف صلاحيات API الداخلية ما دامت العضوية نشطة.
2. موظف الفرع يستطيع قراءة جداول الحركة المالية التفصيلية ضمن فرعه وفق RLS، حتى لو كانت لوحة المالك مخفية عنه.
3. كل الموظفين لهم نفس دور `employee`؛ لا يوجد فصل صلاحيات الاستقبال والفني والمراجع.
4. هوية Auth الفعلية ليست مربوطة بسجل `staff_directory`؛ اسم الموظف المختار حقل إسناد تشغيلي وليس دليل هوية أو صلاحية.
5. حماية كلمات المرور المسربة في Supabase Auth غير مفعلة وفق Security Advisor.
6. Bucket `tenant-site-assets` عام القراءة بالكامل؛ مناسب للأصول العامة، لكنه لا يميز بين صورة منشورة وصورة مسودة. يجب عدم وضع ملفات خاصة فيه.

## 7. المهاجرات وحالة النشر ومصدر الحقيقة

هذه من أهم نتائج التدقيق:
- أداة Supabase لإظهار سجل migrations أعادت قائمة فارغة.
- جدول `public.schema_migrations` يحتوي فقط على baseline `1.0.0`.
- في المقابل، قاعدة TEST تحتوي فعليًا على دوال/محفزات من مراحل لاحقة، منها `create_visit_intake_idempotent` و`publish_report_version` و`save_draft_results_atomic` وRPCs التحصيل والمصروف وتحديث الأسعار.
- توجد أيضًا دالتان في قاعدة TEST غير ممثلتين في migrations الحالية: `consume_patient_portal_attempt` و`set_branch_test_price`.
- لذلك لا يمكن اعتبار عبارة «لم تُنفذ migrations 002–011» صحيحة كحالة حالية، ولا يمكن اعتبار قاعدة البيانات قابلة لإعادة البناء من ملفات المستودع دون مطابقة/تجميع migrations أولًا.
- لا تشغّل ملفات 002–011 عشوائيًا أو تعِد تنفيذها قبل إنشاء خريطة مطابقة بين كل ملف SQL والكائن الفعلي في TEST.
- مصدر GitHub لبوابة المريض أصبح مطابقًا للنسخة المنشورة بعد دفعة إصلاح 01؛ مصدر `publish-report` مطابق أيضًا.

### وثائق قديمة متناقضة

## 9. خطة الإصلاح المجمّعة — دون البدء بتغييرات قاعدة البيانات الحية

### أولوية P0 — قبل اعتماد التشغيل
1. وضع سياسة موحدة لحالة المعمل والاشتراك والفرع، وتطبيقها في صلاحيات قاعدة البيانات/RPC، مع إبقاء مسار آمن للمالك لعرض بياناته أو تصديرها عند التعليق إذا تقرر ذلك.
2. تحديد مصفوفة صلاحيات الموظفين: استقبال، فني، مراجع/معتمد، ومالك؛ ثم حماية البيانات المالية والاعتماد في RLS/RPC وليس إخفاء الروابط فقط.
3. بناء تهيئة مالك المعمل: إدارة الفروع، دعوة حسابات Auth، ربط العضويات بالفروع، وإدارة أسماء الموظفين التشغيلية.
4. توحيد migrations مع قاعدة TEST والنسخة المنشورة، وإضافة ملفات مصدر للدوال الموجودة خارج المستودع قبل أي نشر مستقبلي.
5. نقل إنهاء التحليل واعتماد الزيارة إلى مسارات قاعدة بيانات ذرية، وتثبيت الإسناد الوظيفي وسجل الاعتماد.
6. تصحيح جلب الأسعار ليكون واعيًا بالفرع إذا كانت الأسعار الخاصة بالفروع جزءًا من المنتج.

### أولوية P1 — إكمال دورة التشغيل
7. توحيد سياق الفرع المختار بين الصفحة الرئيسية وكل صفحات التشغيل لتجنب تسجيل البيانات في فرع غير مقصود.
8. تحسين قائمة النتائج: فلترة الحالات النشطة، ترقيم الصفحات، وجلب النتائج دفعة واحدة بدل N+1.
9. توفير تحصيل لاحق للمديونيات مع إيصال/سجل واضح، واختيار طريقة الدفع، وضوابط الخصم.
10. توفير حل تعارض Offline، ومنع إغلاق اليوم مع عمليات محلية معلقة غير مفحوصة.
11. بناء نسخ احتياطي سحابي واستعادة قابلة للاختبار، وتأمين النسخ المحلية وسياسة الاحتفاظ/الخروج.
12. استكمال إعدادات المعمل: الفروع والموظفون وبنود المصروفات والشعار والطباعة وسجل التعديلات.
13. استكمال الموقع العام: صفحة عرض/Renderer ورفع الأصول ومعاينة قبل النشر.
14. تحسين لوحة المالك: pagination، استبعاد الملغى، وتعريف واضح لصافي التحصيل والمديونيات وقيمة التحاليل بعد الخصم.
15. إكمال إدارة الاشتراكات: تواريخ الانتهاء، العدادات، فرض حدود الباقة، والتنبيهات.
16. إضافة واجهة اختيار طريقة الدفع وضوابط الخصم.

### أولوية P2 — التطوير المتقدم
17. تقارير سنوية وربحية التحاليل وBCG وخطة الشهر والتوقعات بعد بناء نموذج تكلفة موثوق.
18. استيراد البيانات التاريخية من Excel وفق ترحيل مضبوط، لا كتابة مباشرة في الجداول الحية.
19. تحسين الفهارس والسياسات وفق استعلامات فعلية وبيانات ممثلة، لا حذف/إضافة عشوائي.
20. تفعيل حماية كلمات المرور المسربة والنظر في MFA لحساب مالك المنصة.
