# Taiba Smart Lab — مراجعة وظيفية أولية (دفعة الاستكشاف 01)

- التاريخ: 18 نوفمبر 2026
- النطاق: قراءة صفحات التطبيق والوحدات المرتبطة بها وملفات الحالة؛ مراجعة ساكنة فقط.
- الحالة: نتائج أولية تحتاج استكمال تتبع SQL والاختبارات والمعاينة الميدانية.
- لا يتضمن هذا التقرير تعديلًا في وظائف التطبيق أو قاعدة البيانات أو النشر.

## 1. ما تمت مراجعته في هذه الدفعة

- شجرة المستودع كاملة على GitHub (190 عنصرًا وقت الفحص).
- صفحات المنصة، لوحة المالك، الاستقبال، النتائج، يوم العمل، الكتالوج، الإعدادات، محرر الموقع، مركز المزامنة، ومدخل التطبيق.
- ملفات JavaScript الرئيسية لعدة شاشات، وسياق المعمل والفرع، ومستودعات الاستقبال والنتائج والتقارير والموظفين، ومحرك Outbox.
- وظيفة بوابة المريض ووظيفة نشر التقارير.
- مصفوفة اختبار RLS، وسجل Batch 25، ووثائق الحالة القديمة.

## 2. نتائج أولية مدعومة بالكود

### 2.1 النظام ليس مجموعة صفحات فقط، لكن اكتمال الترابط لم يثبت
توجد طبقات منفصلة للواجهات والمستودعات وسياق المعمل وقاعدة البيانات والمزامنة. بعض المسارات متصلة بالفعل بمستودعات وRPCs، مثل استقبال الزيارة وحفظ النتائج ونشر التقارير. لكن هذا لا يثبت أن كل الرحلة تعمل end-to-end في المتصفح وعلى قاعدة TEST.

### 2.2 إدارة المعمل لا تزال ناقصة من منظور صاحب المعمل
صفحة `app/settings.html` تعرض هوية المعمل والتواصل والتذييل ورسالة واتساب، وملخص الاشتراك والفروع وروابط مراكز الإدارة.
لكن نص الصفحة يصرّح بأن إدارة بيانات الفروع وحسابات الموظفين ستضاف لاحقًا. لذلك لا يصح اعتبار مركز الإعدادات مكتملًا لإدارة الفروع والموظفين.

### 2.3 دليل الموظف الحالي هو دليل أسماء تشغيلية وليس بالضرورة إدارة حسابات دخول
`modules/staff/repository.js` يتعامل مع جدول `staff_directory` وحقول مثل الاسم والفرع وحالة النشاط. لا تظهر في هذا المستودع عملية إنشاء مستخدم Auth أو ربطه بحساب دخول.
شاشتا الاستقبال والنتائج ويوم العمل تستخدم أسماء/معرفات هذا الدليل لتسجيل الموظف المنفذ. يلزم تتبع سياسات SQL وعلاقات العضويات قبل الحكم على مستوى الإسناد والمساءلة، لكن لا يجوز وصف هذه الشاشة بأنها إدارة حسابات الموظفين حتى يثبت وجود ربط Auth والصلاحيات المقصودة.

### 2.4 فصل مالك المنصة عن مالك المعمل موجود في مسارات منفصلة
إدارة المنصة لها صفحة وملف JavaScript خاصان بها وتستدعي RPC لإدارة المعامل، بينما مساحة المعمل تعتمد على `loadMyTenantContext` وعضويات المعامل والفروع.
المستخدم أكد نجاح دخوله كمالك منصة ورؤية تفاصيل اشتراك طيبة. هذه معاينة يدوية مهمة، لكنها لا تغطي كل أفعال إدارة المنصة ولا اختبارات منع الوصول للبيانات الطبية.

### 2.5 بوابة المريض ونشر التقرير — تصحيح بعد مقارنة المصدر المنشور
- بوابة المريض تستعمل Edge Function بدل إتاحة بحث مباشر عن المرضى للمتصفح، وتعيد رابطًا موقّعًا قصير الصلاحية.
- نشر التقرير يتحقق من جلسة المستخدم، ونوع PDF وحجمه، ويرفع إلى مساحة خاصة ثم يستدعي RPC للنشر، ويحاول حذف الملف إذا فشل النشر.
- النسخة المنشورة من `patient-portal-lookup` في Supabase تستخدم بالفعل RPC ذريًا `consume_patient_portal_attempt`، وبصمات HMAC، ورابطًا موقّعًا قصير الصلاحية. لذلك لا يصح وصف limiter المنشور بأنه غير ذري.
- ملف GitHub الحالي أقدم من النسخة المنشورة ويستخدم عدًّا ثم إدخالًا منفصلين؛ كما أن RPC الذري غير ممثل في migrations بالمستودع. إعادة نشر مصدر GitHub الحالي ستعيد limiter أضعف. يجب توحيد المصدر والمهاجرة قبل أي نشر.
- لم يحدث اختبار استدعاء حي أو رفع PDF أو بحث مريض في هذه المراجعة.

### 2.6 Offline له حدود مقصودة
مركز المزامنة يعرض الانتظار والفشل والتعارضات ويتيح تصدير/استعادة نسخة محلية. الواجهة نفسها توضّح أن النسخة ليست نسخة سحابية كاملة.
محرك Outbox لا يحذف العملية إلا بعد إقرار صريح من معالج المزامنة، ويحتفظ بالتعارضات. مع ذلك، يجب تتبع كل نوع عملية على حدة لمعرفة ما يعمل دون إنترنت وما يبقى Online-only، ثم اختباره على جهاز فعلي.

### 2.7 الوثائق القديمة لا تصلح وحدها لوصف الوضع الحالي
وجدنا أوصافًا قديمة تقول إن طيبة لم تُسجل أو إن عدد المعامل صفر. هذه تتعارض مع فحص TEST السابق ومع تأكيد المستخدم ظهور اشتراك طيبة. يجب الحفاظ على التاريخ مع إضافة توضيح زمني، وعدم تكرار هذه العبارات كحالة حالية.

### 2.8 انتقالات إنهاء التحليل واعتماد الزيارة — تحقق إضافي من محفز النشر

في `modules/results/repository.js`، دالتا `completeVisitTest` و`approveVisit` تنفذان فحص الاكتمال في JavaScript ثم تحديث الحالة بطلب منفصل؛ لا توجد لهما حتى الآن RPCs ذرية مخصصة. وسياسات RLS تسمح لعضو الفرع بتحديث حالة `visits` و`visit_tests` مباشرة.

لكن قاعدة TEST تحتوي على محفز `validate_report_version_publication` يتحقق عند إدراج إصدار منشور من أن كل التحاليل غير الملغاة مكتملة وأن كل بارامتر إلزامي له نتيجة. لذلك **بوابة نشر التقرير تمنع نشر تقرير ناقص** حتى لو تم تغيير حالة الزيارة مباشرة.

**الأثر المتبقي:** يمكن أن تظهر حالة `completed` أو `approved` مبكرًا أو بصورة غير صحيحة قبل النشر، كما أن فحص الواجهة وكتابة الحالة منفصلان وقابلان لسباق التحديث. لا نعد ذلك ثغرة تسمح بنشر تقرير ناقص في ضوء محفز TEST الحالي، لكنه خلل في سلامة انتقال الحالات وسجل الاعتماد.

**الإجراء المقترح:** RPCs ذرية لإنهاء التحليل واعتماد الزيارة، تتحقق من النتائج المطلوبة وحالات التحاليل وصلاحية الفرع وهوية الموظف داخل المعاملة، مع منع التحديثات المباشرة غير المقصودة. لا تُنفذ Migration قبل مطابقة حالة TEST والموافقة.

## 3. فجوات يجب تتبعها قبل اعتماد أي حكم نهائي

1. هل إدارة الموظفين المقصودة هي أسماء تشغيلية فقط، أم إنشاء حسابات دخول وربط كل موظف بعضوية فرع؟ وما الذي تنفذه RLS فعليًا؟
2. هل يمكن للموظف الوصول مباشرة إلى صفحات المالك بكتابة الرابط، وهل تمنع قاعدة البيانات ذلك حتى لو ظهرت الصفحة؟
3. اعتماد الزيارة وإتمام التحليل لا يظهر لهما مسار RPC ذري، لكن محفز نشر التقرير في TEST يمنع نشر تقرير ناقص. يلزم تثبيت انتقال الحالات نفسه داخل قاعدة البيانات.
4. هل صفحة الكتالوج متوافقة تمامًا مع سياسة صاحب المنتج: الموظف يدير البيانات الفنية، والمالك وحده يغير الأسعار؟
5. هل كل عملية مالية تستخدم RPC آمنًا ومفتاح idempotency، أم توجد مسارات مباشرة يمكن أن تتكرر؟
6. هل بوابة المريض ومخزن التقارير خاصان بالفعل مع سياسات Storage صحيحة؟ وهل الرابط الموقّع لا يتجاوز حدود العميل؟
7. هل إعدادات الموقع المنشورة معزولة عن إعدادات المعمل والبيانات الطبية؟ وهل يوجد تدفق واضح لرفع شعار وصور؟
8. هل اختيار المعمل والفرع ينعكس على كل الشاشات والكاش والعمليات المعلقة دون تسرب سياق سابق عند التبديل؟
9. هل يمكن استعادة المعمل بعد فقد الجهاز، أم الموجود حاليًا نسخة محلية فقط؟ ما خطة النسخ السحابي والاستعادة؟

### 3.1 نتيجة مقارنة النشر والمهاجرات

- Edge Function `patient-portal-lookup` المنشورة تختلف عن ملف GitHub؛ النسخة المنشورة تستخدم `consume_patient_portal_attempt` الذري، بينما المصدر يستخدم عدًّا غير ذري.
- Edge Function `publish-report` متطابقة بين المصدر والمنشور.
- أداة migrations في Supabase أعادت سجلًا فارغًا، وجدول `public.schema_migrations` يحتوي baseline `1.0.0` فقط، رغم وجود دوال ومكونات لاحقة في قاعدة TEST. لا يمكن إعادة بناء قاعدة TEST بأمان من ملفات المهاجرات الحالية قبل المطابقة.

## 4. ما لم يحدث في هذه الدفعة

- لم يتم تعديل أي صفحة تشغيل أو JavaScript أو SQL.
- لم يتم تشغيل migrations أو تنفيذ SQL على Supabase.
- لم يتم نشر Edge Functions.
- لم يتم إجراء اختبار متصفح أو هاتف جديد.
- لم يتم إعادة تشغيل الاختبارات الثابتة محليًا؛ أرقام النجاح المذكورة في الوثائق السابقة تظل نتائج تاريخية وليست نتيجة هذه الدفعة.
- لم يتم اعتماد العزل متعدد المعامل أو أمان Storage/بوابة المريض اعتمادًا نهائيًا.

## 5. الخطوة التالية

استكمال التتبع من واجهات كل دور إلى المستودعات وRPCs وسياسات RLS والجداول، مع التركيز على:
1. إدارة المنصة والاشتراك والخطط.
2. الاستقبال والتحصيل والاعتماد المالي.
3. النتائج والاعتماد ونشر التقرير والتصحيح.
4. إعدادات المعمل والفروع والموظفين.
5. المزامنة والنسخ والاستعادة.
ثم إعداد مصفوفة موحدة: الوظيفة، الدور، الشاشة، مصدر البيانات، صلاحية القراءة/الكتابة، دليل الاختبار، والفجوة.
