# دفعة الإصلاح 01 — توحيد مصدر بوابة المريض

**التاريخ:** 18 نوفمبر 2026  
**الحالة:** تغييرات مصدرية على GitHub فقط؛ لا نشر ولا تنفيذ SQL على Supabase.

## المشكلة التي عالجناها

كانت نسخة `patient-portal-lookup` المنشورة في Supabase تستخدم محدد محاولات ذريًا عبر RPC اسمه `consume_patient_portal_attempt`، بينما ملف GitHub كان يستخدم قراءة عدد المحاولات ثم تسجيلها في طلب منفصل. لو أُعيد نشر ملف GitHub القديم، كان سيستبدل الحماية الذرية بنسخة أضعف.

## ما تغير

1. `supabase/functions/patient-portal-lookup/index.ts`
   - تمت مزامنة المصدر مع النسخة المنشورة حرفيًا.
   - يستخدم `consume_patient_portal_attempt`.
   - لا يقرأ جدول محاولات البوابة مباشرة لحساب العدد.
   - يحتفظ بقائمة Origins، وHMAC، ورسائل الخطأ العامة، والرابط الموقّع لمدة 120 ثانية.

2. `database/migrations/012_atomic_patient_portal_rate_limit.sql`
   - أضيف مصدر SQL للدالة الذرية الموجودة بالفعل في TEST.
   - أضيف فهرس على `(ip_hash, attempted_at desc)` لتغطية حد IP العالمي.
   - سُحبت صلاحية التنفيذ من `PUBLIC/anon/authenticated` ومُنحت إلى `service_role` فقط.
   - **لم يتم تشغيل الملف على أي قاعدة بيانات.**

3. `tests/static/patient-portal.test.mjs`
   - تغيرت الاختبارات لتطلب استدعاء RPC الذري وتتحقق من وجود الأقفال وحدود المحاولات وصلاحيات Service Role.
   - لم يتم تشغيل Node test suite؛ المستودع لا يحتوي GitHub Actions workflow، وبيئة التنفيذ الحالية لا تستطيع الاتصال بـGitHub لتنزيل المشروع وتشغيل الحزمة كاملة.

4. تحديث README الخاص بالبوابة وسجل الحالة والتقرير الشامل.

## التحقق بعد التعديل

تمت قراءة الملفات مرة أخرى ومقارنة مصدر GitHub بمصدر Edge Function المنشور:
- تطابق المصدرين: نعم.
- استدعاء RPC الذري: موجود.
- القراءة المباشرة لجدول المحاولات من Edge Function: غير موجودة.
- migration تحتوي advisory locks وحدود 5 محاولات للبحث و20 للمصدر خلال 15 دقيقة: نعم.
- التنفيذ مسموح لـ`service_role` فقط في migration: نعم.

هذا تحقق ساكن من المصدر؛ لا يثبت تشغيل Edge Function بعد نشر جديد، ولم يحدث نشر جديد أصلًا.
