## سجل migrations — ما زال غير مسوّى
هناك سجلان مختلفان:
1. سجل Supabase القياسي يعرض migrations المطبقة 012–022.
2. الجدول التطبيقي `public.schema_migrations` يحتوي سجل baseline واحدًا: `1.0.0`.

ملفات 001–011 في المستودع مرقمة بأسماء مثل `001_initial_schema_v1.sql` وليست ملفات timestamp ضمن `supabase/migrations/`. مجلد `supabase/` الحالي يحتوي `config.toml` وEdge Functions فقط، ولا يحتوي مجلد migrations القياسي.

**القرار:** تم التحقق من وجود بنية baseline ومطابقة الأعمدة الأساسية، لكن لم تتم تسوية سجل Supabase القياسي. لا نضيف أرقامًا/تواريخ مصطنعة، ولا نشغّل 001–011، ولا ننفذ `db push`. يلزم إعداد تاريخ migrations قياسي قابل لإعادة البناء من الصفر، باستخدام Supabase CLI في بيئة تطوير موثوقة، ثم تسجيل migrations القديمة كـapplied دون تنفيذ DDL، بعد مراجعة الملفات والأسماء والترتيب.

تنبيه CLI: Supabase CLI v3 يستخدم `supabase/migrations`، وأوامر قاعدة البيانات تستهدف البيئة المحلية افتراضيًا؛ يجب تحديد `--remote=<project-ref>` صراحة عند التعامل مع TEST، وعدم استخدام أوامر hosted mutation دون مراجعة وموافقة.
